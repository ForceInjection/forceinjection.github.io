# 6740 条 JD 里的 AI Infra 技能版图

> 数据集：国内 12 家 AI 公司官方招聘渠道的在招岗位说明（JD），共 6740 条，采集于 2026-11-19，全部为 JD 全文。按招聘渠道分为**社招 3374 条**与**校招 3366 条**。来源公司：字节跳动、阿里巴巴、腾讯、美团、蚂蚁集团、快手、小红书、阶跃星辰、MiniMax、智谱 AI、月之暗面 Kimi、DeepSeek。

想整理一份 AI Infra 方向的学习材料索引时，遇到一个问题：该学什么、按什么顺序学，现有的说法基本靠个人印象。「推理引擎是核心」「K8s 必须会」这类判断对不对、有多普遍，需要一个市场口径的坐标系。岗位描述（JD）是现成的坐标来源：每一家公司为想要的能力标了价，写明了要求。

这次把 12 家公司的官方招聘入口全部打通：抓取到 34369 个在招岗位（字节社招接口受 1 万条展示上限约束），按「AI Infra / Agent / 大模型训练 / 大模型推理」筛出 6978 条，转换入库 6740 条（6 条状态非「招聘中」跳过、232 条应用算法岗位剔除）。社招与校招分开统计、分开成文，两类岗位的市场画像差异很大，混在一起会互相污染。抓取与转换细节见 [README](README.md)。

产出是数据集本身加六样衍生物：分类报告（`analysis/classification.md`）、技能树（`analysis/skill-tree.md`）两份分析，以及四个可交互页面：社招的 [skill-map-society.html](skill-map-society.html)（技能地图：谱系树、学习路线、技能流向与组合）与 [jobs-society.html](jobs-society.html)（岗位版图：类别分布、城市矩阵、逐条明细检索），校招的 [skill-map-campus.html](skill-map-campus.html) 与 [jobs-campus.html](jobs-campus.html)（同结构，基于校招子集）。分类体系的唯一定义源是 [`data/skill_catalog.json`](data/skill_catalog.json)：六个岗位类别、十六个岗位细分（全部用行业通用岗位名）、十个技能家族、六条岗位线的学习路线，全部脚本只引用这份定义、不做内部定义。这篇文章讲清楚三件事：数据怎么来的、社招与校招各自呈现出的样子、从 JD 到学习路线怎么推导。

## 一、数据怎么来的

12 家公司的招聘系统各不相同：飞书 ATS（字节、智谱、MiniMax）、Moka（阶跃、Kimi、DeepSeek）、各家自建站（阿里、腾讯、美团、快手、小红书、蚂蚁）。抓取工具先抓到 34369 个岗位，再用关键词筛出与 AI Infra / Agent / 大模型训练 / 大模型推理相关的 6978 条，最后转换成统一 schema 入库。

采集原则：取页面正常展示给访客的内容，职责照抄原文，抓不到就记录原因放弃。华为的招聘系统没有公开接口，缺席。

三点采集口径先说清楚，后文的所有数字都受它们影响：

其一，筛选口径是宽的。「大模型训练 / 大模型推理相关」会把算法岗大量收进来，全批算法类 3821 条（占 57%），这些岗位是筛选口径带进来的，看工程岗叙事时应看研发类（2156 条）。

其二，入库时对 title 明写「算法」的岗位做训练/推理相关性判定：title 含模型词（大模型 / LLM / 多模态 / 语音等）的保留，纯应用信号（推荐、搜索、调度、增长、风控等）且正文无训练推理证据的剔除，共剔除 232 条；title 不含「算法」的岗位（如测试开发、运维）不受这一闸门影响。

其三，JD 正文普遍偏短。标题加职责全文的中位数只有 422 字（90 分位 818 字），社招中位数 356 字。这直接影响技能词的命中率，第二节展开。技能词按全文匹配（英文词加边界、量化一词排除交易/分析等非 ML 语境），仍有 349 条（5.2%）一条技能词都没命中。

岗位细分的命名也交代一句：十六个方向全部用行业通用岗位名（大模型算法、Agent 应用、推荐算法、推理系统、训练系统、算子与高性能计算、Infra 工程、平台与调度、网络系统、存储系统、通用研发、产品与运营、测试/评测、SRE、GPU/IDC 运维、模型运维），由 title 关键词规则按优先级派生，规则表就在 skill_catalog.json 里，无命中的落「通用研发」。

## 二、社招版图（3374 条）

**类别分布**：算法 1623 条（48%），研发 1357 条（40%），测试 247 条（7%），SRE 76 条，产品与运营 38 条，运维 33 条。测试、SRE、产品与运营、运维四个小类别合计约 12%，其中 SRE 与运维几乎只从社招招人（全库 SRE 100 条、运维 54 条，社招占 76 与 33）。

**公司分布**：字节跳动 1349 条，占社招的 40%。阿里巴巴 765、腾讯 330、蚂蚁集团 196、美团 147、快手 137、小红书 129 为第二梯队。模型公司体量小但岗位纯度高：阶跃星辰 101、智谱 89、MiniMax 77、Kimi 39、DeepSeek 15。「市场整体」的任何叙事都要记得四成样本来自字节一家的社招口径。

**城市分布**：北京 1912、杭州 1171、上海 1031、深圳 485，四城按提及次数合计约 94%（城市总提及 4887 次）。杭州的构成值得单独看：1171 条里阿里 599、字节 311、蚂蚁 168，阿里仍居半壁，字节快速跟进，杭州的 AI Infra 需求已经是「阿里加字节」的双引擎结构。新加坡 20 条，头部公司的出海岗位开始出现在国内社招渠道里。

**方向分布**：Agent 应用 827 居首，大模型算法 749 次之，通用研发 638 第三。技术方向里，测试/评测 247、Infra 工程 190、推理系统 182、平台与调度 143、训练系统 76、SRE 76；其余细分依次为算子与高性能计算 51、推荐算法 47、网络系统 40、存储系统 37、GPU/IDC 运维 21、模型运维 12。研发类内部，推理系统岗位接近训练系统的两倍半（182 对 76），与推理部署规模化的行业阶段直接相关。

**技能谱系**：社招技能词 81 个，Top 10：大模型/LLM 2226（66%）、Agent框架 1726（51%）、多模态 919（27%）、性能优化 404（12%）、GPU 377（11%）、模型量化 362（11%）、RAG 348（10%）、RLHF 182（5%）、可观测性 155（5%）、Python 140（4%）。

两层口径的解读方式：主题词（大模型/LLM、Agent框架、多模态）说明「这个市场在做什么」；工程技能词说明「写出来的差异化要求是什么」。Python 占比只有 4% 不代表市场不需要 Python：社招 JD 正文普遍短（中位 356 字），这类通用技能常被默认隐含、不进差异化描述。可靠解读是：**写出来的词是岗位的差异化要求**。性能优化（404）、GPU（377）、模型量化（362）、可观测性（155）被高频显式要求，说明调优与稳定性能力已经从加分项变成常规项。

## 三、校招版图（3366 条）

**结构特征先讲清楚**：校招批来自 11 家公司，字节跳动 1519 条占 45%。阿里巴巴 491、腾讯 382、蚂蚁集团 271、美团 200、快手 170、小红书 156 为其后。模型公司校招体量很小（MiniMax 66、阶跃星辰 51、Kimi 46、智谱 14），DeepSeek 的 15 条全部是社招。与社招相比，校招覆盖的公司更少、字节集中度更高（45% 对 40%），校招「市场」实际上更接近「几家大公司的校招口径之和」。

**类别分布**：算法 2198 条（65%），研发 838 条（25%），测试 239 条（7%），产品与运营 46 条，SRE 24 条，运维 21 条。算法岗占 65%，比社招（48%）更高，校招给算法应届生的名额远多于工程应届生。反方向更值得注意：SRE 与运维的校招合计只有 45 条（1.3%），而社招这两类合计 109 条。运维与稳定性岗位几乎完全不走校招渠道，想进这些方向，实习转正或社招是现实路径。

**城市分布**：北京 2043、上海 1296、杭州 1094、深圳 567，四城占比约 97%（城市总提及 5178 次），比社招（94%）更集中。北京的绝对量（2043）超过社招（1912），大公司的校招岗位更多落在总部所在地。杭州的校招构成里阿里 430、字节 322、蚂蚁 241，双引擎结构与社招一致。新加坡 11 条。

**方向分布**：大模型算法 1252 居首，Agent 应用 842 次之，通用研发 371 第三。技术方向里，测试/评测 239、Infra 工程 145、推理系统 140、推荐算法 104、训练系统 86；其余细分依次为网络系统 30、平台与调度 28、算子与高性能计算 27、SRE 24、GPU/IDC 运维 11、存储系统 11、模型运维 10。推理系统对训练系统约 1.6 倍（140 对 86），「推理重于训练」的排列与社招一致。

**技能谱系**：校招技能词 75 个，Top 10：大模型/LLM 2708（80%）、Agent框架 1671（50%）、多模态 1461（43%）、模型量化 373（11%）、性能优化 319（9%）、RAG 291（9%）、GPU 286（8%）、RLHF 190（6%）、推理优化 162（5%）、分布式训练 147（4%）。

与社招对比有两个差异值得说。其一，大模型/LLM 的占比从 66% 升到 80%：校招 JD 的写法更「主题化」，对具体工程工具的要求写得少；Python 在校招只有 85 条（2.5%），分布式训练 147 条、推理优化 162 条反而排在前列。其二，模型量化在校招排到显式要求第四位、压过性能优化（373 对 319；社招是性能优化 404 高于模型量化 362），量化与推理部署是应届生进入推理方向的主要切入口，各公司的校招岗描述里把这个信号写得很明白。

校招渠道里实习岗 1737 条，占校招的 52%：应届进入这个市场的第一步，大多以实习开始。

## 四、按岗位的学习路线

路线的先后顺序是编辑判断：以技能间的依赖关系为主（底层语言先于框架，框架先于调优）、JD 频次为参考，个别低频技能按岗位常识排序（如平台与调度线的 Ray、Go 在 JD 里显式提及很少，但仍属该方向的基本盘），JD 原文本身没有顺序。六条线全部定义在 skill_catalog.json 的 roadmaps 里，页面上每条技能标注该技能在对应方向 JD 中的显式提及条数，数字为全库口径。

**算法线**（算法类 3821 条，公共底座 Python → PyTorch）：

- 大模型算法方向（2001 条）：大模型/LLM → 多模态 → 模型量化 → RLHF → 推理优化
- Agent 算法方向（1669 条）：Agent框架 → RAG → MCP → 多模态
- 推荐算法方向（151 条）：大模型/LLM → 多模态 → 推理优化 → PyTorch → 模型量化

**研发线**（研发类 2195 条，公共底座 Python → Linux → Docker）：

- 推理系统方向（322 条）：模型量化 → KV Cache → 推理优化 → vLLM → SGLang → CUDA → Triton
- 训练系统方向（162 条）：PyTorch → 分布式训练 → RLHF → MoE → 模型量化
- 平台与调度方向（171 条）：Kubernetes → 可观测性 → Ray → Go → Docker
- 算子与高性能计算方向（78 条）：CUDA → Triton → CUTLASS → 性能优化 → GPU
- 网络系统方向（70 条）：RDMA → InfiniBand → RoCE → NCCL
- 存储系统方向（48 条）：NVMe → KV Cache → 性能优化 → GPU

**测试线**（测试类 486 条，底座 Python → Linux）：AI 测试 / 评测方向：CI/CD → 大模型/LLM → Agent框架 → 模型量化 → 性能优化。测试岗的标题已经以模型与 Agent 系统的评测为主。

**SRE 线**（SRE 类 100 条，底座 Linux → Python）：平台稳定性方向：SLA/SLO → 可观测性 → GPU → 故障排查 → RDMA。SRE 岗的 AI 化程度高：四成 SRE 岗把 GPU 写进了技能要求。

**运维线**（运维类 54 条，底座 Linux → Python）：

- GPU/IDC 运维方向（32 条）：大模型/LLM → GPU → Kubernetes → 模型部署 → SLA/SLO
- 模型运维方向（22 条）：大模型/LLM → Agent框架 → RAG → 模型部署 → GPU

**产品与运营线**（84 条，无技术底座）：大模型/LLM → Agent框架 → 多模态 → 模型量化 → 模型部署。这是六条线里唯一的非技术线：产品与运营岗不写代码，但要能对齐模型能力边界、Agent 产品形态与量化部署的成本账，这条链按该方向 JD 的显式提及频次排出。

校招求职者的使用方式：算法线与研发线的入口技能（Python、PyTorch、分布式训练、模型量化）在校招 JD 里有直接频次，照路线学习即可；SRE 与运维两条线校招名额极少（合计 45 条），应届进入主要靠实习转正。校招渠道的实习岗 1737 条与算法线、研发线的前三个方向高度重合，可以作为切入口统计。

## 五、总评

这份数据把几个流传甚广的印象摆到了数字面前：研发类内部，推理系统岗位（322 条）是训练系统（162 条）的两倍，「推理时代」在招聘口径上成立；模型量化（735 条）排在全库显式要求第四位，但与性能优化（723 条）只差 12 条，两者构成第一梯队，调优能力从加分项变成常规项；RDMA（127 条）仍是一百多个岗位的显式要求，而 InfiniBand 修正匹配口径后只剩 26 条：写 IB/InfiniBand 的多是网络专岗，高速互联的普及度远没有 RDMA 高；测试类 486 条岗位中近九成以模型或 Agent 系统为评测对象，AI 测试已经是成建制的招聘方向。社招与校招的分册统计还补了两个常被忽略的事实：SRE 与运维几乎不招应届，入口在实习与社招；产品与运营作为唯一的非技术类别单独成类，它要求的技术词汇与工程岗高度重叠，差别在深度而不在广度。

引用这份数据时的折扣清单：

1. **筛选口径偏宽**。算法类 3821 条（57%）是筛选口径带进来的算法岗总和，其中的 Agent 应用 1669 条里约六成 title 是工程岗（研发/开发/架构词），「AI Infra 岗位」的严格口径应剔除或单独说明，研发类 2195 条是更严格的工程口径；
2. **字节占 43%**（社招 40%、校招 45%）。类别、方向、技能的分布都被字节的招聘口径主导，跨公司结论需按公司分层；
3. **方向由 title 关键词规则派生**。规则表在 skill_catalog.json，无命中的落「通用研发」（1009 条，占 15%）；title 关键词无法区分同一方向内的算法岗与工程岗；
4. **技能词是全文匹配**。英文词加了边界、量化一词排除交易/分析等语境，仍有 349 条（5.2%）未命中任何技能词；responsibilities 字段里约 15% 的记录混入了原文的任职要求段（来源职责与要求本就合并在一段）；
5. **salary 与 level 字段全空**（来源不提供），薪资与职级维度不可分析；
6. **华为与百度缺席**，无法覆盖；
7. 数字随招聘进度每日变动，采集于 2026-11-19，引用前建议核对最新抓取。
